## 1. WHAT THIS SECTION IS SAYING

The **Preview controls** section is about what happens when you use:

```bash
mkdocs serve
```

In other words:

> **How does MkDocs behave while you're developing and previewing your documentation locally?**

The settings here control things such as:

* what directories MkDocs watches for changes
* what URL structure the generated site uses
* whether warnings stop the build
* what local address the development server uses

## `watch`

### What MkDocs is saying

`watch` tells MkDocs about **additional directories** that it should monitor for changes when you run:

```bash
mkdocs serve
```

It is a YAML list.

```yaml
watch:
  - directory_a
  - directory_b
```

Normally MkDocs watches the relevant project files automatically.

`watch` lets you add more directories to that set.

### Why would you need this?

Suppose you have files outside the normal locations that affect your documentation.

You can tell MkDocs:

> “Also watch these directories. If something changes there, reload the preview.”

Instead of having to specify:

```bash
mkdocs serve -w directory_a -w directory_b
```

every time, you can put the directories in `mkdocs.yml`.

---

## Important path distinction

There are **two different ways** of specifying watch paths.

### In `mkdocs.yml`

```yaml
watch:
  - directory_a
```

The path is relative to the **configuration file**.

### On the command line

```bash
mkdocs serve --watch directory_a
```

The CLI-provided path is **not** relative to the configuration file.

This distinction is specifically called out by MkDocs.

So:

```text
Configuration-file watch path
        ↓
relative to mkdocs.yml

CLI --watch path
        ↓
not relative to mkdocs.yml
```

## `use_directory_urls`

This setting controls the **directory structure of the generated site** and therefore the URL format used to link to pages.

There are two modes:

```text
false
true
```

The difference is significant.

---

## `use_directory_urls: false`

This mode is useful when the hosting system **cannot serve `X/index.html` when the URL is simply `X`**.

When set to `false`, MkDocs doesn't create a directory containing `index.html` for each page.

Instead, it creates an `.html` file directly.

For example:

```text
Source                 Generated file          URL

index.md               index.html              /index.html

api-guide.md           api-guide.html          /api-guide.html

about/license.md       about/license.html      /about/license.html
```

So:

```text
api-guide.md
    ↓
api-guide.html
    ↓
/api-guide.html
```

rather than:

```text
api-guide.md
    ↓
api-guide/index.html
    ↓
/api-guide/
```

### Why might you need this?

MkDocs specifically gives examples such as:

* opening documentation pages directly from the filesystem
* publishing documentation to a static S3 website

So if your hosting environment requires direct file access, `false` can be appropriate.

---

# `use_directory_urls: true`

This is the **default**.

Instead of making the URL point directly to an `.html` file, MkDocs organizes pages into directories containing:

```text
index.html
```

For example:

```text
Source                 Generated file              URL

index.md               /index.html                 /

api-guide.md           /api-guide/index.html       /api-guide/

about/license.md       /about/license/index.html   /about/license
```

The important transformation is:

```text
api-guide.md
     ↓
api-guide/index.html
     ↓
/api-guide/
```

This produces what MkDocs describes as more **user-friendly URLs**.

### Default

```yaml
use_directory_urls: true
```

---

## The fundamental difference

Think of the two modes like this:

### `false`

```text
Markdown
   ↓
HTML FILE
   ↓
URL points to FILE
```

### `true`

```text
Markdown
   ↓
directory/index.html
   ↓
URL points to DIRECTORY
```

So this setting isn't about whether MkDocs generates HTML.

**Both modes generate HTML.**

It is about **how the generated HTML files are organized and how their URLs are exposed.**

# `strict`

`strict` controls how MkDocs handles **warnings**.

```yaml
strict: true
```

means:

> If MkDocs raises a warning, stop processing.

```yaml
strict: false
```

means:

> Print the warning, but continue processing.

### Example

Imagine MkDocs finds a broken link.

With:

```yaml
strict: false
```

you might get:

```text
warning
    ↓
display warning
    ↓
continue
```

With:

```yaml
strict: true
```

you get:

```text
warning
    ↓
treated as fatal
    ↓
processing stops
```

There is also a command-line equivalent:

```bash
mkdocs build --strict
```

### Default

```yaml
strict: false
```

## `dev_addr`

`dev_addr` specifies the address used by:

```bash
mkdocs serve
```

It must have this format:

```text
IP:PORT
```

The default is:

```text
127.0.0.1:8000
```

So MkDocs' development server normally runs at:

```text
http://127.0.0.1:8000/
```

You can configure a different default:

```yaml
dev_addr: 127.0.0.1:9000
```

This saves you from having to provide:

```bash
--dev-addr
```

every time you run `mkdocs serve`.

### Default

```yaml
dev_addr: '127.0.0.1:8000'
```

```text
markdown_extensions
```

They operate at different levels.

```text

      ↓
```

# `markdown_extensions`

MkDocs uses the **Python Markdown** library to convert Markdown files into HTML.

So the basic pipeline is:

```text
Markdown
   ↓
Python Markdown
   ↓
HTML
```

Python Markdown has **extensions** that change or add to how Markdown is interpreted.

MkDocs lets you enable those extensions using:

```yaml
markdown_extensions:
```

MkDocs itself uses these extensions by default:

```text
meta
toc
tables
fenced_code
```

You can add more.

---

## Enabling an extension

For example, to enable the Python Markdown **SmartyPants** typography extension:

```yaml
markdown_extensions:
  - smarty
```

This means:

```text
markdown_extensions
       ↓
     smarty
       ↓
enable this Markdown extension
```

### Default

```yaml
markdown_extensions: []
```

The displayed default is an empty list because this setting represents **additional extensions you configure**; MkDocs still has its own built-in/default extensions.

---

# Extensions can have their own configuration

An extension may expose its own settings.

For example, the built-in `toc` extension supports:

```text
permalink
```

You can configure it like this:

```yaml
markdown_extensions:
  - toc:
      permalink: true
```

Notice the YAML structure:

```text
- toc:
    permalink: true
```

The colon after:

```text
toc:
```

turns `toc` into a mapping whose value contains another mapping.

---

## Multiple options

An extension can have several options:

```yaml
markdown_extensions:
  - toc:
      permalink: true
      separator: "_"
```

Each option gets its own line and indentation.

Conceptually:

```text
toc
├── permalink → true
└── separator → "_"
```

---

## Multiple extensions

You add another list item for each extension:

```yaml
markdown_extensions:
  - smarty
  - toc:
      permalink: true
  - sane_lists
```

So:

```text
- smarty
      ↓
extension with no custom options

- toc:
    permalink: true
      ↓
extension with configuration

- sane_lists
      ↓
another extension with no custom options
```

---

# Dynamic configuration values

MkDocs allows extension configuration values to be obtained dynamically.

The documentation points to two mechanisms:

### Environment variables

Values can come from environment variables.

### Current paths

Values can use paths associated with:

* the Markdown file currently being rendered
* the overall MkDocs site

These capabilities are covered elsewhere in the Configuration documentation.

---

# Alternative syntax for extensions

Instead of representing extensions as list items:

```yaml
markdown_extensions:
  - smarty
  - toc:
      permalink: true
  - sane_lists
```

you can represent them as **key/value pairs**:

```yaml
markdown_extensions:
  smarty: {}
  toc:
    permalink: true
  sane_lists: {}
```

There is one important difference.

For an extension with no options, you must explicitly provide an empty value:

```yaml
smarty: {}
```

rather than simply:

```yaml
smarty:
```

The `{}` represents an **empty mapping**.

---

## Why does MkDocs mention this alternative syntax?

Because it becomes **required when using configuration inheritance** and you want to override options in inherited configurations.

So this isn't merely two interchangeable styles for aesthetic reasons.

The alternative mapping syntax has a specific practical use later in the configuration system.

---

# More extensions

Python Markdown provides many extensions that can be used without installing something separately.

There are also **third-party extensions**.

MkDocs points users toward:

* Python Markdown's extension documentation
* the Python Markdown third-party extension ecosystem
* the MkDocs project catalog

Third-party extensions may have their own installation procedures and configuration options.

The key point is:

```text
Python Markdown
       ↓
built-in extensions
       +
third-party extensions
       ↓
customize Markdown processing
```

# `hooks`

**New in MkDocs 1.4**

`hooks` lets you specify Python scripts that MkDocs loads and uses as plugin instances.

Example:

```yaml
hooks:
  - my_hooks.py
```

The path is relative to:

```text
mkdocs.yml
```

The Python file can contain **plugin event handlers**.

For example:

```python
def on_page_markdown(markdown, **kwargs):
    return markdown.replace('a', 'z')
```

This function runs when MkDocs processes page Markdown and returns modified Markdown.

---

## What is a hook actually doing?

The important conceptual model is:

```text
MkDocs event
     ↓
hook function
     ↓
your custom Python logic
     ↓
result returned to MkDocs
```

For example:

```text
Markdown
   ↓
on_page_markdown()
   ↓
modify Markdown
   ↓
MkDocs continues processing
```

---

# Advanced hook example

MkDocs gives an example where a hook scans Markdown for non-HTTPS links and generates warnings.

The script:

```python
import logging, re
import mkdocs.plugins

log = logging.getLogger('mkdocs')

@mkdocs.plugins.event_priority(-50)
def on_page_markdown(markdown, page, **kwargs):
    path = page.file.src_uri
    for m in re.finditer(r'\bhttp://[^) ]+', markdown):
        log.warning(f"Documentation file '{path}' contains a non-HTTPS link: {m[0]}')
```

The important idea isn't memorizing the Python.

The hook:

```text
reads Markdown
    ↓
looks for http:// links
    ↓
logs a warning
```

And because warnings can become fatal under:

```bash
mkdocs build --strict
```

this can effectively turn the hook into a documentation-quality check.

---

# Hooks versus plugins

MkDocs explicitly says hooks don't provide new capabilities compared with plugins.

Instead, hooks simplify **one-off uses**.

A plugin generally needs to be installed as a plugin package.

A hook can simply be a Python file in your project.

So:

```text
plugin
   ↓
reusable/installed extension mechanism

hook
   ↓
simple project-local customization
```

The hook system is therefore particularly convenient when you need a small piece of custom behavior for one project.

---

## `mkdocs-simple-hooks`

The documentation notes that this functionality may look familiar if you've used the:

```text
mkdocs-simple-hooks
```

plugin.

A configuration using that plugin can sometimes be replaced directly with the built-in `hooks` configuration.

Old:

```yaml
plugins:
  - mkdocs-simple-hooks:
      hooks:
        on_page_markdown: 'my_hooks:on_page_markdown'
```

New:

```yaml
hooks:
  - my_hooks.py
```

---

## Important `mkdocs serve` behavior

When using:

```bash
mkdocs serve
```

the hook module is **not reloaded on every build**.

That's an important development-time caveat.

Changes to the hook itself therefore don't necessarily behave like changes to ordinary watched documentation content.

---

## MkDocs 1.6 — adjacent imports

MkDocs 1.6 made another improvement.

If the hook file has another Python file next to it:

```text
hooks/
├── my_hooks.py
└── foo.py
```

the hook can use normal Python syntax:

```python
import foo
```

to access functions from `foo.py`.

Older versions required a workaround involving:

```python
sys.path
```

# `plugins`

`plugins` specifies the plugins MkDocs should use when building the site.

It is a YAML list, and each plugin can optionally have its own configuration.

### Default

MkDocs provides:

```text
search
```

by default.

So conceptually:

```yaml
plugins:
  - search
```

is the default plugin configuration.

---

# Important behavior when you define `plugins`

This is a major MkDocs configuration rule.

If you explicitly define:

```yaml
plugins:
```

you **replace the default plugin configuration**.

You don't merely add to it.

Therefore, if you write:

```yaml
plugins:
  - your_other_plugin
```

you have removed the default:

```text
search
```

plugin unless you explicitly add it back.

So:

```yaml
plugins:
  - search
  - your_other_plugin
```

means:

```text
keep search
+
add your plugin
```

---

## Disabling all plugins

To completely disable plugins:

```yaml
plugins: []
```

This also disables the default `search` plugin.

---

# Configuring a plugin

A plugin can have its own options.

For example:

```yaml
plugins:
  - search
  - your_other_plugin:
      option1: value
      option2: other value
```

The structure is:

```text
plugin
   ↓
configuration mapping
   ↓
individual plugin options
```

---

# `enabled`

**New in MkDocs 1.6**

Every plugin has an `enabled` Boolean option supplied by MkDocs.

This lets you conditionally enable or disable a plugin.

For example:

```yaml
plugins:
  - search
  - code-validator:
      enabled: !ENV [LINT, false]
```

Here `enabled` receives a value from an environment variable through the `!ENV` YAML tag.

So the conceptual chain is:

```text
environment variable
        ↓
      !ENV
        ↓
     enabled
        ↓
 plugin on/off
```

---

# Alternate plugin syntax

Plugins can also use mapping syntax rather than list syntax.

Instead of:

```yaml
plugins:
  - search
  - your_other_plugin:
      option1: value
      option2: other value
```

you can write:

```yaml
plugins:
  search: {}
  your_other_plugin:
    option1: value
    option2: other value
```

Again, the plugin with no options needs:

```yaml
{}
```

The documentation specifically says this alternative syntax is **required for configuration inheritance** when overriding plugin options.

# Search plugin

MkDocs includes a **Search plugin** by default.

It uses:

```text
Lunr.js
```

as its search engine.

The available settings control how MkDocs builds and uses the search index.

Those settings are:

```text
separator
min_search_length
lang
prebuild_index
indexing
```

---

# `separator`

`separator` is a **regular expression** that tells the search indexer which characters should be treated as word separators.

The default is:

```text
[\s\-]+
```

This means whitespace and hyphens are treated as separators.

For example, you could add the dot:

```yaml
plugins:
  - search:
      separator: '[\s\-\.]+'
```

Now the dot is also treated as a word separator.

### Default

```text
[\s\-]+
```

---

# `min_search_length`

This is an integer specifying the **minimum number of characters a search query must contain**.

The default is:

```text
3
```

So searches shorter than three characters are ignored.

Why?

MkDocs says short search terms generally produce poor-quality search results.

But there are legitimate cases where short terms matter.

For example, documentation about **Message Queues** might naturally involve:

```text
MQ
```

which is only two characters.

You could therefore configure:

```yaml
plugins:
  - search:
      min_search_length: 2
```

### Default

```text
3
```

---

# `lang`

`lang` specifies the languages used when building the search index.

Languages are identified using **ISO 639-1 language codes**.

For example:

```text
en → English
fr → French
de → German
ja → Japanese
```

MkDocs/Lunr Languages supports the listed languages:

```text
ar  Arabic
da  Danish
nl  Dutch
en  English
fi  Finnish
fr  French
de  German
hu  Hungarian
it  Italian
ja  Japanese
no  Norwegian
pt  Portuguese
ro  Romanian
ru  Russian
es  Spanish
sv  Swedish
th  Thai
tr  Turkish
vi  Vietnamese
```

You can configure multiple languages.

---

## Why not just add every language?

MkDocs warns against doing that unless you actually need them.

Each additional language increases:

* bandwidth requirements
* browser resource usage

The documentation therefore recommends generally keeping each MkDocs instance to a single language.

---

## Chinese and other Asian languages

The documentation notes that Lunr Languages does not currently include support for Chinese or some other Asian languages.

It says some users have reported decent results with Japanese.

That is a limitation of the search-language support, not a general statement about whether MkDocs can contain Chinese documentation.

---

## Default language

The default value is:

```text
theme.locale
```

if you've configured `theme.locale`.

Otherwise:

```text
[en]
```

So:

```text
theme.locale
      ↓
search language
```

when a locale is explicitly set.

---

# `prebuild_index`

This optionally generates a **pre-built search index** containing the site's pages.

The purpose is performance.

It can improve search performance on larger sites.

Set:

```yaml
plugins:
  - search:
      prebuild_index: true
```

to enable it.

But the documentation says to first make sure your theme explicitly supports a prebuilt index. The built-in themes do.

---

## Node.js requirement

This option requires:

```text
Node.js
```

to be installed, with:

```text
node
```

available on the system path.

If MkDocs tries to call Node.js and it fails:

```text
warning
   ↓
build continues
```

rather than automatically stopping.

However, if you use:

```bash
--strict
```

the warning can become an error.

---

## Small site versus large site

The documentation makes an important performance distinction.

For smaller sites, a pre-built index isn't recommended because:

```text
more bandwidth
      +
little/no noticeable benefit
```

For large sites—particularly hundreds of pages—the tradeoff can make more sense:

```text
larger index/bandwidth cost
      +
significant search-performance improvement
```

---

# `indexing`

`indexing` controls **how much content the search index contains**.

Example:

```yaml
plugins:
  - search:
      indexing: 'full'
```

There are three options.

| Setting    | What gets indexed                         |
| ---------- | ----------------------------------------- |
| `full`     | Title + section headings + full page text |
| `sections` | Title + section headings                  |
| `titles`   | Title only                                |

So:

```text
full
 ↓
maximum searchable content

sections
 ↓
title + headings

titles
 ↓
title only
```

The documentation notes that this is particularly useful for large projects where the search index itself becomes very large and consumes significant disk space.

| **pre-built index**       | A search index generated in advance rather than built in the browser                       |
| **bandwidth**             | Amount of data transferred over a network                                                  |
| **browser resources**     | CPU, memory, network and related resources used by the browser                             |
| **locale**                | Language/region setting                                                                    |
| **ISO 639-1**             | Standard using two-letter codes to identify languages                                      |
| **third-party extension** | Extension developed outside the core project                                               |
| **one-off**               | Something intended for a particular project/use rather than a reusable installed component |
| **conditional**           | Behavior that depends on whether a condition/value is true or false                        |

---

# 3. SYNTAX / NOTATION

## Extension list syntax

```yaml
markdown_extensions:
  - smarty
```

The `-` means:

> This is one item in the list.

---

## Extension with options

```yaml
markdown_extensions:
  - toc:
      permalink: true
```

The structure is:

```text
list
 ↓
toc
 ↓
mapping of options
 ↓
permalink: true
```

---

## Mapping syntax

```yaml
markdown_extensions:
  toc:
    permalink: true
```

This is structurally different from the list form.

The empty mapping:

```yaml
smarty: {}
```

means:

> `smarty` is configured, but has no options.

---

## Plugin configuration

```yaml
plugins:
  - search:
      min_search_length: 2
```

means:

```text
plugins
  ↓
search plugin
  ↓
min_search_length
  ↓
2
```

---

## Regular expression

```text
[\s\-\.]+
```

You don't need to memorize the individual regex symbols from this page yet.

For MST purposes, the important meaning is:

> This is a pattern that tells the search system which characters count as word separators.

---

## Search indexing levels

```text
full
sections
titles
```

These aren't YAML types; they're **allowed values for the `indexing` configuration option**.

# 4. HOW THE PIECES CONNECT

The Formatting options section has three different extension mechanisms.

## Markdown extensions

```text
Markdown
   ↓
Python Markdown
   ↓
markdown_extensions
   ↓
how Markdown is interpreted/formatted
```

These primarily affect **Markdown processing**.

---

## Hooks

```text
MkDocs event
     ↓
hooks
     ↓
your Python function
     ↓
custom action
```

These let you insert project-local Python logic into MkDocs' processing events.

---

## Plugins

```text
MkDocs build
     ↓
plugins
     ↓
additional functionality
```

Plugins are the more general MkDocs extension mechanism.

---

## Search

The built-in Search plugin then has its own configuration:

```text
plugins
   ↓
search
   │
   ├── separator
   │
   ├── min_search_length
   │
   ├── lang
   │
   ├── prebuild_index
   │
   └── indexing
```

So don't mentally treat these as six independent MkDocs systems.

They are **options belonging to the Search plugin**.
